# 任务名 / Task name

- 类型 / Type：修 bug 还是做需求 / bug fix or feature
- 当前状态 / Status：进行中 / 已完成 / 卡住

> **写账本要说人话**：给一个不了解这套系统的初级工程师看，他要能看懂"干了什么、现在什么状态、下一步做什么"。
> **先人话、后术语**；术语要么不用、要么在同一份账本里第一次出现时用一句话解释。
> **说人话不省证据**：命令与原始输出照旧要贴在该条后面（通常是"结果"那行，原始输出可贴代码块）。
> **写详细，要能"回看"**：万一要退回重做，判断"上一版错在哪"全靠这份账本。所以每条除了结论，还要写清**依据**——**读了什么 / 跑了什么命令看到什么 / 由此得出什么结论**；尤其 `analyze`、`plan`、`tdd` 三步要写细。**仍然是三行**（干了啥 / 结果 / 下一步），依据并进"结果"里，不要加第 4 个字段。
> **`review` 每次判 FAIL 都要写一条判词**（为什么没过 + 问题清单）：这是被打回的那一步唯一能知道"上一版错在哪"的地方。**判词只留在对话里 = 退回重做时瞎改。**
> **Write in plain language**: a junior engineer unfamiliar with this system must be able to tell "what was done, current state, what's next".
> **Plain first, jargon second**; avoid jargon or explain it in one line the first time it appears in this ledger.
> **Plain language never excuses missing evidence** — the command and raw output still go in the entry (usually under "Result"; raw output may be in a code block).
> **Write it in detail — it must support "looking back"**: if you fall back and redo, the ledger is how you judge "what was wrong in the previous version". So each entry records its **grounds**, not just its conclusion — **what was read / what command was run and what it printed / what conclusion follows**; `analyze`, `plan` and `tdd` especially. **Still three fields** (did / result / next); fold the grounds into "Result" — do not add a fourth field.
> **`review` writes a verdict on every FAIL** (why it did not pass + the problem list): that is the only place the sent-back step can learn what the previous version got wrong. **A verdict left only in the conversation means the fallback is flying blind.**
>
> **开工建账本时，必须把 `progress/` 加进本项目的 `.gitignore`**（固定动作，不是可选项）——这样任何 git 回退都碰不到账本。
> **When you create the ledger, you MUST add `progress/` to this project's `.gitignore`** (a fixed action, not optional) — then no git revert can touch the ledger.

## 日期 · 第1步：复现问题 / 看懂需求（进行中）
- **需求原文**：把用户给的截图 / 原话**逐字**贴这里（界面名、日志噪音不算原文；拿不准就整段贴，并标出哪句是 R1、哪句是 R2）。读不了图就让用户把文字打出来，照抄，不许复述补全。
- 干了啥：一句话说清这一步在干什么（人话）。
- 结果：一句话说清现在什么状态/看到了什么现象；**再补依据**：读了什么、跑了什么命令、看到什么原始输出、由此得出什么结论。
- 下一步：一句话说清接下来要做什么。

## 日期 · 第2步：定位原因 / 分析代码（进行中）
- 干了啥：一句话说清这一步在干什么（人话）。
- 结果：一句话说清现在什么状态；**再补依据**（读了什么 + 命令 + 原始输出 + 结论）。
- 下一步：一句话说清接下来要做什么。

## 日期 · 第3步：出方案（进行中）
- 干了啥：拆任务（每条带可验证的完成标准 + **落点**）+ **做影响面分析**（列出要改的既有符号、逐个搜使用方）+ **做架构落位**（这次改动放在哪、跨不跨边界、动没动契约、9 条基线逐条判）。
- 结果：任务清单 + 完成标准 + **用例落点** + **影响面清单**（下面这张，**必交**；确实没改既有符号的写"本次未改动既有符号"+**依据**——`git diff` 涉及哪些文件、为什么里面没有既有符号）+ **架构落位**（下面那节，**必交**）。
- 下一步：派独立 agent 评审方案 → 给用户确认。

**用例落点**（每条 A 编号的用例最后落在仓库哪个文件；`单测`/`端到端` → 测试文件，`人工` → 清单文件）

### 架构落位（必交）

进哪些路径：<具体路径 / glob>

| 8.2 绕过入口 | 涉及 / 不涉及 | ... |
| 8.3 横切件单入口 | 涉及 / 不涉及 | ... |

| 8.5 数据单写入口 | 涉及 / 不涉及 | ... |
| 8.6 失败当成功 | 涉及 / 不涉及 | ... |
| 8.7 加载期配置 | 涉及 / 不涉及 | ... |
| 8.8 可见性 | 涉及 / 不涉及 | ... |
| 8.9 共享状态写入 | 涉及 / 不涉及 | ... |

> **"不涉及"要拿证据说话**：每条"不涉及"必须附**仓库级搜索命令 + 原始输出**（同"搜了没有"的标准）。
> **8.1 / 8.3 / 8.5 / 8.7 的"不涉及"不许只用"在 diff 里没看到"来证明**——它们的违例可能整个在 diff 之外。
> **裁定规则：9 条里凡标"不涉及"却没给命令的 → 本步不算完成。**
> **这份落位也跟代码走**：④ commit 时抄进 commit message 的 `## 架构落位` 小节（**只放结论**，命令留在账本里）。**中途改过落位** → 在本节**追加**一条修订记录（不重写历史），commit message 同步。

> **这份清单要跟着代码走**：④ commit 时抄进 commit message 的 `## 影响面` 小节。账本会删，它不能跟着消失——出问题时 `git log` 是唯一还留着"这次碰过什么"的地方。
> **确实没动既有符号时（豁免，不是默认路径）**：不能只写一句话，要交**下面这张表**（`git diff` 涉及的每个文件都列出），⑦会逐行拿 diff 对着核：

| 文件 | 这个文件里有哪些既有符号 | 为什么它们没被改 |
|---|---|---|
| ... | ... | 只新增未改动 / 新代码没有接管它 / ... |

> **只新增文件也要列**：新代码有没有挂到某个既有入口上（新路由接管路径 / 新分支改既有判断 / 新注册项顶替原实现）——"没改文件但改了行为"最容易漏。

## 日期 · 第7步：独立评审（进行中）<!-- 预填示例：按实际轮次删改；判了几次 FAIL 就写几条 -->
- 干了啥：派独立 agent 复查（谁评的、评了什么；**含独立核对影响面清单**：自己搜一遍，看有没有漏掉的使用方；**含独立核对架构落位**：拿落位对着 diff 核，并**自己重跑每条"不涉及"的命令**）。
